<h1 align="center">confidence-tree-ts</h1>

<p align="center"><b>部品の組み合わせ方を壊して、誰も気づかない場所を見つけ、一度得た確信を失わせない。</b></p>

<p align="center">TypeScript のための、確信の台帳。</p>

---

> **Status: 設計。** この README は、試作 `ctp` での実験結果をもとに、ゼロから書き直した設計の宣言です。
> 何が確かめられていて、何がまだかは、[ここまでにわかっていること](#ここまでにわかっていること)にあります。

バグの多くは、部品の中ではなく、部品のあいだで起きます。呼び忘れ、渡し忘れ、条件の片方の見落とし、偽物と本物の食い違いです。部品のテストをいくら足しても、ここへの確信は増えません。カバレッジも、ここを測れません。3 つのファイルを別々のテストで実行しただけでも、行カバレッジは満たされてしまうからです。

confidence-tree-ts は、3 つのことをします。

| | すること | 誰が使うか |
| --- | --- | --- |
| **探す** | 欠陥の集まる関数の組み立て箇所を壊してみて、どのテストも気づかない場所を見つける | エージェント |
| **守る** | 一度検出できた壊し方は、以後も検出され続けることを、CI で保証する | CI |
| **決める** | 実装から推定した振る舞いが仕様かどうかを、人に短く尋ね、答えを記録する | 人（エージェント経由） |

```
$ ct find --hotspots

src/cli/commands.ts#record                       fix 13 件
  ◌ 空回り   after: flags.after          どのテストも到達しない
  ◌ 空回り   fps: flags.fps              どのテストも到達しない
  ◍ 素通り   sheet: flags.sheet          到達: tests/cli/record.test.ts · 消しても落ちない
  ● 検出     outDir: resolve(flags.out)

src/runtime/start.ts#start                       fix 6 件
  ◍ 素通り   if (!rail.available() || presenter.isOpen()) {
             「|| presenter.isOpen()」を落としても落ちない

候補 4 件を台帳に足すには:  ct find --hotspots --propose > confidence/proposals.yaml
```

## 考え方

**確信とは、組み立て点を壊すと、テストが落ちることである。** テストがあることも、コードを実行したことも、確信ではありません。組み合わせ方を壊したときに気づけるかどうか、だけを確かめます。

**いちばん効くのは、どこが組み立て点かを名指しすることである。** 組み立て点を名指しされたエージェントは、自分で壊して確かめるところまでできます。高くつくのは、組み立て点を見つけることのほうです。だからこのツールは、見つけることに力を使います。

**確信は増やすことを強制せず、失うことだけを止める。** CI が新しい確信を要求すると、導入した日から赤くなり、運用が続きません。一度検出できた壊し方が検出できなくなったときだけ、CI を止めます。確信は、単調にしか増えません。

**正しさは人が決め、人への質問はエージェントが運ぶ。** 実装から推定した振る舞いが仕様かどうかは、人にしか決められません。人は CLI を叩かずに、エージェントとの会話の中で答えます。ツールは、その質問を短く正確にすることと、答えを改ざんしにくい形で記録することを担います。

## クイックスタート

```sh
bun add -d confidence-tree-ts        # npm i -D / pnpm add -D でも可
bunx ct init                          # ct.config.ts、confidence/、AGENTS.md の約束を置く
```

あとは、エージェントに頼みます。

```
> ct find --hotspots の上位 3 つについて、台帳に主張を足して、テストを書いて
```

エージェントは、次の順で作業します。

1. `ct find --hotspots` で、空回りと素通りの候補を得る
2. 候補を主張の文に直し、台帳に書く
3. テストを書き、`ct prove` で保持になるまで直す
4. 出どころが実装しかない主張について、`ct ask` の質問をあなたに見せる
5. あなたの答えを `ct decide` で記録する
6. `ct show` の結果を報告する

あなたがすることは、4 の質問に答えることだけです。

## 台帳

台帳は `confidence/*.yaml` に置きます。単位は**主張**です。ファイルでもノードでもありません。

```yaml
# confidence/signup.yaml
area: signup

claims:
  validation#clear-on-fix:
    text: 直したら、その欄のエラーを消す
    source: defect "#412"
    joins:
      - in: src/features/signup/useSignupForm.ts#onChange
        code: validateField(field)
    assumes: [rules#required, rules#format]
    tests:
      - src/features/signup/useSignupForm.test.ts > メールを直すと、メール欄のエラーだけが消える

  validation#revalidate-on-change:
    text: 入力が変わったら、その欄だけ検証をやり直す
    source: impl
    joins:
      - in: src/features/signup/useSignupForm.ts#onChange
        order: [setValue, validateField]
    tests:
      - src/features/signup/useSignupForm.test.ts > 入力を変えると、その欄だけ検証し直す

  api#returns-user:
    kind: boundary
    text: 登録に成功すると、サーバーが返したユーザーを画面に出す
    source: type packages/contracts/signup.ts
    joins:
      - in: apps/web/src/features/signup/api.ts#signup
        code: return parseUser(await res.json())
      - in: apps/api/src/routes/signup.ts#post
        code: return c.json(toUser(row))
    fakes: [apps/web/test/fakes/signup-server.ts]
    tests:
      - apps/e2e/signup.spec.ts > 登録するとユーザー名が表示される

  api#fake-keeps-contract:
    kind: contract
    text: 偽物のサーバーは、本物と同じ契約で答える
    source: type packages/contracts/signup.ts
    contract: packages/contracts/signup.contract.ts
    against:
      - apps/api/src/routes/signup.ts
      - apps/web/test/fakes/signup-server.ts

  rules#required:
    kind: unit
    text: 必須の欄が空なら、その欄を不正にする
    source: spec docs/signup.md#検証
    tests: [src/features/signup/rules.test.ts]

retired:
  validation#validate-on-blur:
    reason: 仕様変更で、検証は入力ごとに行うことになった
    replaced-by: validation#revalidate-on-change
```

### フィールド

| フィールド | 意味 |
| --- | --- |
| `text` | 正しく動くと言いたいことを 1 文で。テストの期待値はここから決まる |
| `source` | 根拠。`spec` `ticket` `defect` `commit` `type` `impl` `decision` のいずれか |
| `kind` | `glue`（既定）、`boundary`、`contract`、`unit` |
| `joins` | 組み立て点。`in` はファイルとシンボル、`code` はシンボルの中で一意なコード片、`order` は呼ぶ順序 |
| `breaks` | 手で書いた壊し方（省略可）。生成する壊し方で足りないときだけ書く |
| `assumes` | この主張が前提にする、別の主張。ここで保持している振る舞いは、この主張のテストでアサートしない |
| `fakes` | テストで使う偽物。偽物を書いたら、それを本物に留める `contract` の主張が必要 |
| `tests` | 主張を確かめるテスト（`ファイル > テスト名`）。`unit` 以外では、ファイル全体の指定は警告になる |

### 木は書かない、描かれる

主張どうしの `assumes` をたどると、木（厳密には DAG）が描けます。木の形を別に書く必要はありません。`ct show` が描きます。

### 状態は書かない、導かれる

主張の状態は台帳に書きません。`prove` の結果と、人の判断の記録から、毎回導かれます。

| 記号 | 状態 | 意味 |
| --- | --- | --- |
| `●` | 保持 | 有効な壊し方のすべてで、テストが落ちる |
| `◍` | 素通り | 壊した組み立て点にテストが到達したのに、落ちなかった |
| `◌` | 空回り | 組み立て点に、テストが到達していない（偽物を動かしている、テストの中で組み直している） |
| `○` | 未検証 | テストがない |
| `↻` | 要再確認 | 組み立て点かテストが、前回から変わった |
| `?` | 判定不能 | 変更前のコードでもテストが落ちる、または有効な壊し方がない |

これとは別に、出どころが `impl` の主張には、人の判断の状態が付きます。

| 記号 | 判断 | 意味 |
| --- | --- | --- |
| `◐` | 未判断 | 仕様かどうか、まだ誰も答えていない |
| `✓` | 仕様 | 人が仕様だと答えた |
| `✗` | 欠陥の候補 | 人が仕様ではないと答えた。いまの実装が間違っている |
| `…` | 保留 | 答えた人にはわからなかった。持ち主に尋ねている |

## 探す：ct find

`ct find` は、台帳がなくても動きます。関数を指定すると、その中の組み立て箇所を機械的に壊し、どのテストも気づかない場所を挙げます。

```sh
ct find --hotspots                     # fix コミットが集まる関数の上位から
ct find src/cli/commands.ts#record     # 関数を指定して
ct find --hotspots --propose           # 台帳に貼れる主張の下書きを出す
```

### 流れ

1. **候補を集める。** 関数の中の、呼び出し、条件の項、代入、戻り値、オブジェクトに渡す値を、組み立て箇所の候補にする
2. **到達の地図を作る。** すべての候補にプローブを入れ、テストファイルを 1 つずつ動かす。どのテストファイルが、どの候補に到達したかがわかる
3. **到達しなかった候補は、壊さずに空回りとする。** どのテストも通らない場所は、壊しても気づけない
4. **到達した候補だけ、壊して確かめる。** 動かすのは、その候補に到達したテストファイルだけ
5. **結果を並べる。** 関数ごとに、空回りと素通りを先に並べる

到達の地図は、import の関係ではなく、実際の実行から作ります。だから、テストが spawn した CLI の中の箇所も、ブラウザで動く箇所も、正しく到達として数えられます。import をたどってテストを選ぶと、こうした箇所は見落とされます。

### 壊し方

生成する壊し方は、組み合わせ方の「欠落」を中心にしています。組み合わせ方の誤りの多くが、入れ替えではなく、何かが抜けることだからです。

| 候補 | 壊し方 | 想定する誤り |
| --- | --- | --- |
| 呼び出し | 消す | 副作用の呼び忘れ |
| 条件 | 項を 1 つ落とす、偽にする、真にする | 条件の片方の見落とし、機能検出の誤り |
| 代入 | 消す | 状態の書き戻し忘れ |
| オブジェクトに渡す値 | そのプロパティを消す | 値の渡し忘れ |
| 戻り値 | 早く返す | 処理の途中での打ち切り |

`--propose` は、空回りと素通りの候補を、台帳に貼れる形で出します。主張の文は空欄です。文を書くのはエージェントで、決めるのは人です。

## 確かめる：ct prove

`ct prove` は、台帳の主張について、組み立て点を壊してテストが落ちるかを確かめます。エージェントが、テストを書いたあとに手元で使います。

```
$ ct prove signup

signup/validation#clear-on-fix          ●  検出 4/4
signup/validation#revalidate-on-change  ●  検出 2/2       ◐ 未判断
signup/api#returns-user                 ◌  apps/api/src/routes/signup.ts#post に到達なし
                                            テスト 1 件は apps/web/test/fakes/signup-server.ts だけを動かしている
```

`prove` が当てるのは、生成した壊し方と、台帳の `breaks` です。CI だけが当てる隠した壊し方は、ここには含まれません（[守る](#守るct-guard)を参照）。

## 守る：ct guard

`ct guard` は CI で動きます。PR が、一度得た確信を失わせていないかを確かめます。

```yaml
# .github/workflows/confidence.yml
- run: bunx ct check
- run: bunx ct guard --base origin/main --comment
  env:
    CT_SEED: ${{ secrets.CT_SEED }}
```

### ラチェット

| 状況 | CI |
| --- | --- |
| 基準で検出されていた壊し方が、検出されなくなった | **止める** |
| 基準で保持していた主張が、保持でなくなった | **止める** |
| 主張が、`retired` に理由を書かずに消えた | **止める** |
| まだ保持していない主張がある | 表示するだけ |
| 新しい壊し方が、検出されなかった | 表示するだけ |
| 組み立て点が変わって、要再確認になった | やり直す。やり直した結果で判断する |

基準は、main の最新の `guard` の結果です。CI がキャッシュとして持ち、リポジトリにはコミットしません。PR では、PR が触った組み立て点と、そのテストに関わる主張だけをやり直します。全体のやり直しは、夜間に回します。

等価な壊し方（どんなテストでも検出できないもの）は、一度も検出されないので、CI を止めることがありません。等価かどうかを、人が判断する必要はありません。

### 隠した壊し方

`guard` は、エージェントが見ていない壊し方を、生成して当てます。エージェントが見た壊し方だけに合わせてテストを書くことを防ぐためです。

- 乱数の種は、組み立て点のコードのハッシュと、CI だけが持つ `CT_SEED` から作ります。エージェントには予測できません
- 組み立て点のコードが変わらないかぎり、同じ壊し方が当たり続けます。PR と関係のない場所で突然落ちることはありません
- 隠した壊し方が生き残ったら、PR のコメントで開示します。開示した壊し方は、以後は見える壊し方として扱います

### PR のコメント

```
確信の変化（main との比較）

  - signup/api#returns-user        ● → ◌   後退：テストが偽物のサーバーに置き換わった
  + signup/validation#clear-on-fix  ◍ → ●
  ~ signup/form#submit-payload      ↻ やり直し → ●

この PR で記録された人の判断（2 件）
  ✓ signup/validation#revalidate-on-change   「1 は仕様です」 hajimism · エージェント経由
  ✗ signup/form#trim-email                   「いや、それはバグ。前後の空白は送る前に消すべき」 hajimism · エージェント経由

隠した壊し方で生き残ったもの（開示）
  signup/validation#clear-on-fix   validateField(field) の条件を真にする
```

## 決める：ct ask と ct decide

人が判断するのは、出どころが実装しかない主張だけです。人は CLI を使いません。エージェントが質問を運び、答えを記録します。

### 流れ

```
エージェント   ct ask --format chat          質問をそのまま人に見せる
人             会話の中で答える                「1 は仕様、2 はバグ、3 はわからない」
エージェント   ct decide <質問> <答え> --quote "<人の言葉>"
CI            PR のコメントに、判断と人の言葉を並べる
レビュアー     PR の承認で、判断を確定する
```

### 質問の形

`ct ask` は、エージェントが言い換えずにそのまま見せられる質問を出します。言い換えると、質問が誘導的になったり、根拠が抜けたりするからです。

````
$ ct ask --format chat

確認させてください（2 件）。番号で答えてください。

**1. 入力が変わったら、その欄だけ検証をやり直す**
いまの実装がそうなっていますが、仕様として書かれた根拠が見つかりませんでした。

```ts
// src/features/signup/useSignupForm.ts:29-32
const onChange = (field: Field) => (v: string) => {
  setValue(field, v)
  validateField(field)   // ← ここ
}
```

  1. 仕様です（テストで固定します）
  2. 違います（バグとして記録します）
  3. 書き直します（正しい振る舞いを教えてください）
  4. わかりません（コードの持ち主に聞く文面を作ります）

**2. メールアドレスの前後の空白を、そのまま送る**
…
````

質問には、次の決まりがあります。

- **1 回に 5 件まで。** 重要なものから並べます。glue と boundary の主張、fix コミットに近い主張が先です
- **根拠のコードを必ず付ける。** 人が、コードを開かずに判断できるようにします
- **選んだ結果どうなるかを、選択肢に書く。** 「仕様です」を選ぶと、その振る舞いがテストで固定されることを、人が知ったうえで答えられるようにします
- **「わかりません」を必ず用意する。** わからないのに「仕様です」と答えさせないためです。`git blame` から組み立て点の持ち主を推し、その人に聞く文面を `ct ask --for <人>` で作ります

`--format json` を使うと、選択肢つきの構造で出ます。ボタンで答えられる UI を持つエージェントは、こちらを使ってください。選択肢の文言は、そのまま使います。

### 答えの記録

```sh
ct decide q-7f3a spec --quote "1 は仕様です"
ct decide q-91c0 bug  --quote "いや、それはバグ。前後の空白は送る前に消すべき"
ct decide q-c2e4 rewrite --text "入力が変わったら、すべての欄の検証をやり直す" --quote "全部やり直す、が正しい"
ct decide q-0b8d unsure --quote "わからない。鈴木さんが書いたはず"
```

記録は `confidence/decisions.jsonl` に、1 行 1 件で追記されます。

```json
{"claim":"signup/validation#revalidate-on-change","text":"sha256:4be1…","question":"sha256:9f2c…","answer":"spec","quote":"1 は仕様です","by":"hajimism","via":"agent","at":"2026-11-24T10:31:07+09:00"}
```

- `text` は主張の文のハッシュです。文が 1 文字でも変われば、判断は外れて未判断に戻ります
- `question` は、人に見せた質問のハッシュです。エージェントが `ct ask` の質問をそのまま見せたことを、後から確かめられます
- `quote` は、人が実際に言った言葉です。PR のコメントにそのまま並ぶので、レビュアーは、エージェントの要約ではなく、人の言葉を見て確かめられます
- `rewrite` の場合、新しい文の主張ができ、その出どころは `decision` になります。人が書いた文なので、未判断にはなりません
- `bug` の場合、主張は欠陥の候補になり、`ct gaps` の先頭に「仕様と違う実装」として出ます

### この仕組みが防げることと、防げないこと

エージェントは、人に聞かずに `ct decide` を実行できてしまいます。これは仕組みでは防げません。防げるのは、それが**見えないまま通ること**です。

- 判断はすべて、人の言葉と一緒に PR のコメントに並びます
- `decisions.jsonl` を CODEOWNERS の必須レビューにすれば、判断は人の承認なしには main に入りません
- 判断を消したり書き換えたりすると、`ct check` が落ちます。判断は追記だけです

## 読む：ct gaps / ct show / ct check

### ct gaps

エージェントが次に書くテストを、1 つずつ返します。

```
$ ct gaps signup

1. signup/api#returns-user                       boundary · 型 · ◌ 空回り
   確かめること   登録に成功すると、サーバーが返したユーザーを画面に出す
   到達しない点   apps/api/src/routes/signup.ts#post   return c.json(toUser(row))
   ヒント         既存のテストは fakes/signup-server.ts を動かしている。本物のサーバーを立てるか、契約で留めた偽物を使う
   確かめなくてよいこと
     - 必須・形式の判定そのもの   rules#required, rules#format で保持済み
```

並び順は、欠陥の候補、空回り、素通り、未検証の順です。それぞれの中では、boundary、glue、出どころが仕様のものの順です。

### ct show

台帳を、`assumes` をたどった木として描きます。保持だけの部分木は、既定で畳みます。

```
$ ct show signup

signup                                   ● 3  ◍ 0  ◌ 1  ○ 0   ◐ 1
├─ validation#clear-on-fix               ●  検出 4/4
│  └─ rules#required, rules#format       ●  畳み（2）
├─ validation#revalidate-on-change       ●  検出 2/2   ◐ 未判断
└─ api#returns-user           boundary   ◌  到達なし: apps/api
   └─ api#fake-keeps-contract  contract  ●  本物 ✓ 偽物 ✓
```

| オプション | すること |
| --- | --- |
| `--all` | 畳んだ部分木も開く |
| `--only gaps` | 保持していない主張と、その祖先だけ |
| `--base <ref>` | 基準との差を重ねる（`+` 改善、`-` 後退、`~` 変化） |
| `--boundaries` | パッケージをまたぐ主張だけを、地図として描く |
| `--ascii` | 記号を ASCII にする |

端末でないとき（パイプやファイルへの出力）は、色を付けず、ID も省略しません。エージェントは、この出力をそのまま報告に使えます。

### ct check

台帳が壊れていないかを確かめます。違反は、直し方と一緒に返ります。

1. すべての主張に、出どころがある
2. `glue` と `boundary` の主張に、組み立て点がある
3. すべての組み立て点が、指したシンボルの中に一意に見つかる
4. `fakes` に書いた偽物には、それを本物に留める `contract` の主張がある
5. fix コミットや欠陥チケットのうち、台帳の範囲のファイルに触れたものは、いずれかの主張に対応している
6. 消えた主張は、`retired` に理由がある
7. `decisions.jsonl` は追記だけで、消された行も書き換えられた行もない

```
✗ E103 signup/validation#clear-on-fix: 組み立て点が見つからない
  in:   src/features/signup/useSignupForm.ts#onChange
  code: validateField(field)
  直し方: onChange の中の該当箇所を探して code を直す。組み立て方が変わったなら、主張の文も見直す
```

## エージェントとの約束

`ct init` が `AGENTS.md` に書き足す内容です。

```md
## Confidence Tree

- 台帳のない場所では、`ct find --hotspots` の候補から主張を書く
- テストを足す前に `ct gaps` を読み、上から順に埋める
- 期待値は主張の文から決める。実装の出力を写さない
- `assumes` で保持している振る舞いは、アサートしない
- glue と boundary のテストでは、組み合わせ方そのものを偽物に置き換えない。偽物を使うなら、`contract` の主張で本物に留める
- 書いたら `ct prove` を通す。空回りと素通りは、保持になるまで直す
- 出どころが実装しかない主張を書いたら、作業の終わりに `ct ask --format chat` の質問を、言い換えずにそのまま人に見せる
- 人の答えは、その人の言葉のまま `ct decide --quote` で記録する。人に聞かずに `ct decide` を実行しない
- 主張を消すときは `retired` に理由を書く
- `decisions.jsonl` を手で編集しない
- 作業の終わりに、`ct show --only gaps` の結果と、記録した判断の件数を報告する
```

### MCP

`ct mcp` は、次のツールを MCP で提供します。

| ツール | 中身 |
| --- | --- |
| `ct_find` | `ct find --json` |
| `ct_gaps` | `ct gaps --json` |
| `ct_prove` | `ct prove --json` |
| `ct_check` | `ct check --json` |
| `ct_ask` | 選択肢つきの質問。ボタンで答えられる UI にそのまま渡せる形 |
| `ct_decide` | 答えの記録。`quote` が空なら拒否する |

## 判定の仕組み

### 到達と破壊を分ける

到達は、壊していないコードにプローブだけを入れて測ります。破壊は、プローブを入れずに壊し方だけを当てて測ります。テストが組み立て点を通るかどうかは、壊すかどうかと関係がないからです。

```
到達     プローブを入れて、主張のテストを動かす
           変更前のコードでも落ちる → 判定不能（落ちたテストの名前を出す）
           到達しない              → 空回り
破壊     壊し方を当てて、主張のテストを動かす
           構文が通らない           → 無効（数えない）
           落ちた                  → 検出の候補
           通った                  → 生存
確認     検出の候補だけ、もう一度壊して動かす
           2 回とも同じ理由で落ちた → 検出
           それ以外               → 判定不能
```

### プローブ

プローブは、自己完結した 1 つの式です。バッククォート、`${`、バックスラッシュを含みません。ブラウザに送るコードを文字列として持っているファイル（テンプレート文字列の中のコード）にも置けるようにするためです。

プローブは、到達の印を 2 か所に書きます。`CT_PROBE` で渡したファイルと、ローカルの HTTP の受け口です。Bun や Node のプロセスからはファイルが確実に届き、ブラウザからは HTTP だけが届きます。どちらに届いたかは、結果の `via` に残ります。

### 偽の検出を防ぐ

検出が誤ると、偽の保持になります。これはこのツールでいちばん悪い誤りです。だから検出だけは、次のように確かめます。

- 検出の候補は、もう一度壊して動かし、2 回とも落ちることを確かめる
- 落ちた理由を、アサーションの失敗、例外、時間切れに分ける。時間切れは検出に数えない
- 落ちるまでの時間が、変更前のコードでの所要時間より大きく伸びていたら、判定不能にする。テストの中の待ち時間切れが、普通の失敗として報告される場合があるからです

### 1 つずつ壊す

既定では、壊し方を 1 つずつ当てます。まとめて当てて二分する方式（`--batch`）もありますが、試作では、壊し方が少なく生き残りの多い構成で、1 つずつのほうが速くなりました。`--batch` は、壊し方が数百を超えるときの選択肢です。

## 設定

```ts
// ct.config.ts
import { defineConfig } from "confidence-tree-ts";

export default defineConfig({
  runner: "bun",                        // "bun" | "vitest" | "jest" | "playwright"
  ledger: "confidence/*.yaml",
  hotspots: {
    fixCommits: /^(fix|bugfix)(\(.+\))?:/,
    since: "12 months ago",
  },
  prove: {
    timeout: "120s",
    jobs: 4,
  },
  workspaces: true,                     // pnpm / npm / yarn / bun のワークスペースを読む
  packages: {
    "apps/e2e": { runner: "playwright" },
  },
});
```

TypeScript と JavaScript だけを対象にします。シンボルの解決には TypeScript の構文木を使うので、`file#symbol` の指定と、リファクタへの強さは、この言語に限って高い精度で保てます。

## 運用の形

| 形 | すること | 手間 |
| --- | --- | --- |
| **監査** | 四半期に 1 回などで `ct find --hotspots` を流し、空回りと素通りの一覧からテストを足す。台帳は残さない | ほぼない |
| **ラチェット** | 欠陥の集まる数十か所だけ台帳に載せ、CI は後退だけを止める | 小さい。人の判断が月に数件、台帳の手入れはエージェント |
| **全面** | 主要な機能すべてを台帳に載せ、`ct gaps` でエージェントのテストを導く | 大きい |

ほとんどのリポジトリには、ラチェットが合うはずです。監査から始めて、欠陥がはっきり集まっている場所が見えたら、そこだけ台帳に載せてください。

台帳の大きさが、運用の手間を決めます。台帳は小さく保つものです。

## ここまでにわかっていること

試作 `ctp` で、dek（Bun の TypeScript のリポジトリ）を題材に確かめたことです。

**確かめられたこと**

- 組み立て点に絞って壊し、到達を別に測ると、手作業の調査結果と判定が一致した。2 つのコミットで偽の保持は 0 件、食い違いは環境が原因の 1 件だけ
- 組み立て点のテストを足すと、その主張だけが保持に変わり、ほかの判定は変わらなかった
- プローブは、テストのプロセス、spawn した CLI、dev サーバー、happy-dom、実ブラウザ（テンプレート文字列の中のコード）のすべてから届いた
- 6 か所と対照、12 の主張の判定が、約 1 分で終わった
- 調べた 6 か所のうち 5 か所は、生成できる壊し方で表せた
- 組み立て点のコードを書き換えると、`check` が見つからないことを報告した

**試しの 1 回で観察したこと（まだ数えていない）**

- 組み立て点のコード片を渡されたエージェントは、判定を受け取らずに、対象の 8 件すべてを保持にした。頼まれずに、自分で行を消して確かめていた
- 判定を受け取ったエージェントも 8 件を保持にしたが、隠した壊し方を 1 件取りこぼした

この観察が、「名指しが効く」「見つけることに力を使う」「隠した壊し方を CI で当てる」という、この設計の 3 つの柱のもとになっています。条件を分けた比較（組み立て点を渡さない条件、エージェントが自分で探す条件）は、まだ実施中です。

## やらないこと

- **カバレッジを測らない。** 実行したことは、確信ではありません
- **確信を増やすことを強制しない。** CI が止めるのは、後退だけです
- **点数を出さない。** 点数は、上げることが目的になります
- **木を import から作らない。** 候補は、実際に壊して実行した結果から出します
- **テストを書かない。** 書くのはエージェントです
- **人の代わりに判断しない。** エージェントにも、判断させません
- **TypeScript 以外を対象にしない。** 狭くすることで、深く正確にします

## 未解決の設計

- **組み立て点を探す範囲。** いまは、fix コミットが集まる関数の中だけを探します。関数をまたぐ組み立て（同じ組み立てが 3 か所に書かれているもの）は、まだ見つけられません
- **偽物の自動検出。** `fakes` は人かエージェントが書きます。テストの中で使われている偽物を、ツールが自動で見つけられるかは、まだわかりません
- **持ち主に聞く流れ。** `ct ask --for` は文面を作るだけです。持ち主の答えを、誰がどう記録するかは決めていません
- **ブラウザのバンドルの再ビルド。** 試作の題材では、テストのたびにソースからビルドしていたので不要でした。ビルド済みのバンドルを読むテストでは、壊すたびに再ビルドが要ります
